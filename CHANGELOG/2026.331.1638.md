# 2026.331.1638 — fix(session): the nested Plasma session can no longer lock itself, and layer-kde-shell advances

## Summary

Closes opencharly/pod-kde-nested#6.

The nested Plasma session armed Plasma's screen locker, so a streamed desktop showed the greeter after
idle and no unattended VNC capture could see the desktop. This change disables the locker in the image
and advances the session's own package set.

- **`charly.yml` (candy `kde-nested`)** — a `write:` of `~/.config/kscreenlockerrc`
  (`[Daemon] Autolock=false, Timeout=0, Lock=false, LockOnResume=false`) plus a build-scope check that
  the file carries `Autolock=false`, `Lock=false` and `Timeout=0`.
- **`require:`** — `layer-kde-shell` `v2026.326.2019` → **`v2026.330.2234`** (the current release of
  the session's own package set).
- **A BED, so the claim is covered in-tree** — `kde-nested-bed-image` (CDI GPU pod base + the smallest
  host that can carry the session: `pod-sway` headless + `pod-wayvnc`) and `check-kde-nested-locked`,
  whose `bed-unlocked-after-idle` step waits SEVEN MINUTES (past the 300 s Timeout) and then asserts
  there is no `kscreenlocker_greet` and `ScreenSaver.GetActive` is not true.

Nothing else changes: the launcher, the sockets, the bus choice and the capability strip are
untouched.

```

$ charly cmd kde-lock-clean "... pgrep -fc kscreenlocker_[g]reet; ScreenSaver.GetActive ..."
```

The keys are the ones the image's own schema declares (`/usr/share/config.kcfg/kscreenlockersettings.kcfg`:

### The bed (`check-kde-nested-locked`) on this tree

```
$ charly check run check-kde-nested-locked
[image-build] PASS after 7m17.052s [advisories=2]
[check-live]  PASS after 7m15.782s
PASS (steps=16, skipped_checks=14)                          EXIT=0
  check-live.log: 43 steps: 41 passed, 0 failed, 2 skipped

PASS  the host compositor, the VNC server and the nested session are all RUNNING   [bed-services]
PASS  the image carries the session's unlock policy                                [kde-nested-bed-image-policy]
PASS  the nested session has NOT locked itself after Plasma's idle Timeout         [bed-unlocked-after-idle]
```

The two counters are two phases' accounts: `PASS (steps=16, skipped_checks=14)` is the BOX phase (its
14 skips are the `[runtime]`-scoped declared checks the engine cannot run without a deploy), and
`43 steps: 41 passed, 0 failed, 2 skipped` is the LIVE phase. The `[advisories=2]` on the image build
are the project-wide multi-tag resolution notices the same build prints on an unmodified tree — not
warnings; `box validate` reports `0 warnings, 0 errors` above.

`bed-services` compares the de-duplicated supervisor states to `RUNNING` EXACTLY (a `contains: RUNNING`
on a `sort -u` list passes when any one service is up, which is a check that cannot fail for its
description; the image candy also checks the policy itself, at build time).

`bed-unlocked-after-idle` sleeps 420 s and then requires BOTH instruments to answer positively —
no `kscreenlocker_greet` process AND `ScreenSaver.GetActive` = `false` — so a dead session bus fails
the step instead of reading as "unlocked". The wait is the measurement: the control below is unlocked at 30 s and locks
only past the 5-minute Timeout, so time is the only discriminating instrument — and this step now
FAILS on an image without the config.

### Spike

RCA claim: the lock is kscreenlocker's idle lock; its master switch is `Daemon/Lock`, and the
settings schema names all four keys.

```
# (a) Autolock=false + Timeout=0 + LockOnResume=false, written into a RUNNING session, then
#     `supervisorctl restart kde-nested`
after: greeters=1 locked=true uptime=0:05:49            ← locked, but CONFOUNDED: restart path
# → and the same experiment was invalid for a second reason found here: `deploy add` reuses the
#   EXISTING image, so the written file was never in an image at all (`cat: no such file`).

# (b) the same keys PLUS Lock=false, present in the IMAGE at session start, no restart (CHOSEN)
t-now: greeters=0 locked=false uptime=0:08:04           ← unlocked past the timeout

# (c) PowerDevil / display-power settings, i.e. the lock being a "lock on resume" after the display
#     powers down. NOT a candidate for THIS cause, and the measurement says so rather than a guess:
#     (b) differs from the control in exactly ONE variable — the kscreenlockerrc file in the image —
#     and the behaviour flipped (locked → unlocked). A PowerDevil-driven lock would have ignored
#     `Daemon/Lock=false` and still locked, so (b)'s success discriminates the cause to the locker's
#     own idle lock. The resume path is covered anyway: `LockOnResume=false` is in the same file.
```

Winner: **(b)**. The RCA holds: the lock is the idle lock and `Daemon/Lock` is its master switch —
`Autolock=false`/`Timeout=0` alone did not stop it, while adding `Lock=false` (in an image, not a
running session) did.
